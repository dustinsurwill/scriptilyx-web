## Context

Scriptilyx SE is a Windows/WPF desktop app for visually building Space Engineers programmable-block scripts. This project (`wirerig`) is a from-scratch web app — React + TypeScript + React Flow, deployed as a static site to GitHub Pages — that reproduces the tool's functionality in the browser, with no backend, plus one new feature the desktop app never had: a script **minifier** to help stay under Space Engineers' practical script-size limits. Thresholds are checked against the real programmable-block limit (100,000 characters, confirmed against the in-game editor) rather than a guessed number — green under 80,000, amber 80,000–95,000, red above 95,000.

This ships from a brand-new, independent repo, not a fork of the original — no shared git history, binaries, or source with it. The README credits/links the original project.

Fully static/no-backend is intentional and sufficient: the whole app is load-JSON → edit-graph-in-memory → generate-string. Storage is `localStorage` autosave plus manual file export/import — both client-only.

## IP handling (binding constraint on everything below)

We are not the original author (ChaosVROne) and not authorized by them. The original repo deliberately ships no source and no LICENSE — that's "all rights reserved" by default, not an oversight. The original app's source code is never committed here or referenced in code comments/commits; any local research into how it behaves is kept entirely outside this repo.

`NodeLibrary.json` / `ConveyorSorterItems.json` are reused verbatim as the node database — plain data (block names, categories, action ids, UI copy) already shipped publicly in the app's own releases — credited in the data file header and README. That credit stays regardless of this project's own name/branding, as long as this data is shipped.

The codegen engine is a clean-room reimplementation: built from the node *spec* (`NodeLibrary.json`'s `Title`/`Description`/`Preview`/ports/properties) and the public Space Engineers Programmable Block API — ModAPI XML docs shipped with the game, and the malforge/keensoftwarehouse public API references — never from the original app's code. See `docs/space-engineers-codegen-api-notes.md` for the source-by-source breakdown.

This posture extends to every additional game, not just Space Engineers: Stationeers' IC10 catalog/codegen (`src/games/ic10/`) is likewise original content built from IC10's own public instruction-set documentation, with no equivalent third-party node-database JSON to reuse verbatim (unlike `NodeLibrary.json`, there's no public data file to credit here — the catalog is hand-authored). See `docs/ic10-api-notes.md` for its source-by-source breakdown, in the same spirit as the Space Engineers notes.

## Tech stack

- **Vite + React + TypeScript** for the app shell.
- **React Flow (`@xyflow/react`)** for the canvas — infinite pan/zoom, custom node components, `Handle`-based ports, edge drawing.
- **Zustand** for graph state — an action-based store with real undo/redo.
- No backend, no database. `localStorage`/`IndexedDB` for autosave, `Blob` + `<a download>` for exports, `<input type="file">` for imports, Clipboard API for "Copy Script".

## Data layer

- `NodeDefinition`, `NodePropertyDefinition` (`Type: "text"|"multiline"|"number"|"combo"|"bool"`, `DefaultValue: string`, `Options: string[]`), `ScriptNode`, `NodeConnection`, `GraphSaveData` as TypeScript types.
- Ship `NodeLibrary.json` (345 node defs, 16 categories) as a static asset, loaded at startup, credited to the original project.
- **Save file compatibility**: keep the `.segraph` format (plain indented JSON of `{Nodes, Connections, NextNodeNumber, Zoom}`) as the export/import schema, so users' existing desktop-app save files open directly here. Our own defensive load-time validation (reject non-finite coordinates, default missing fields, clamp zoom), designed independently against the schema.
- Conveyor sorter/inventory item picker (item id fields like `ItemId`/`ItemType`): deferred to the stretch milestone — see 7.1 below. (Node pack import/management, previously also slated for 7.1, was dropped: there's no node-pack JSON in hand to build against, so it'd be UI for a format nobody's produced yet.)

## Canvas / editor (React Flow)

- Custom React Flow node component: header (title + number badge), left-stacked input `Handle`s, right-stacked output `Handle`s, preview text (substitute `{PropertyName}` tokens into `NodeDefinition.Preview`). Port counts are dynamic per node.
- **Connection rule**: one outgoing wire per output port (connecting a new one replaces the old); an input port can receive multiple incoming wires. Enforced in React Flow's `onConnect` handler.
- Deleting a node cascades to delete its incident edges (React Flow default).
- Zoom/pan via React Flow's built-in infinite viewport; persist zoom into `GraphSaveData.Zoom` on save for file-format parity.
- Property panel driven by `NodePropertyDefinition.Type`: `text`/`number` → single-line input (no min/max — parity with the original, validated only at generate-time), `multiline` → textarea (monospace when the key is `"Code"`), `combo`/`bool` → select dropdown (`bool` defaults to `["true","false"]` if `Options` is empty).
- Node palette/search: sidebar grouped by `Category`, live substring filter against `Title`, `Category`, `Search`, `ActionType`.
- Validation panel: pure function `getGraphIssues(nodes, edges)` (no Start node, multiple Start nodes, unreachable nodes, unconnected output ports, empty/non-numeric property values, dangling edges).

## Codegen engine — clean-room reimplementation, single design

One engine, designed from the node spec and the public SE API, with two independent options:

- `multiTickBudget?: { maxNodesPerTick: number }` — tick-budgeted state machine (one dispatch case per node id, explicit "next node" pointer, per-tick node-count budget, yields via `Runtime.UpdateFrequency = Update1`) for graphs too large for one game tick. Unset → straight recursive emission for small/medium graphs.
- `professionalComments?: boolean` — toggles a generated header comment summarizing the graph.

Always compile each node to exactly one case/function referenced by id (never inline per-branch), so a node reachable via two branches is only ever emitted once.

Pieces: graph traversal (DFS/BFS from `Start`, global visited set), an `ActionType → code emitter` table (one entry per `NodeDefinition`, written against SE's public API + each node's own `Preview`/`Description`), an on-demand helper-method library, property coercion utilities, and validation (no/multiple Start nodes, unreachable nodes, unconnected required ports, non-numeric `number` properties, dangling connections, plus size-based warnings).

## Multi-game architecture (Milestone 8+)

Turns this from a single-game tool into a "pick a game" shell. Each game lives under `src/games/<id>/` and exports one `Game` object (`src/types/game.ts`): `nodeDefinitions`, `generate()`, an optional `minify()`, an optional `remapLegacyGraph()` (only Space Engineers has a legacy desktop-app format to import from), and optional `templates`/`wizards`/`itemList`. `src/games/registry.ts` collects every game's export into one `games` map the landing page and router read from.

Key finding from the Space Engineers codegen deep-dive that shaped this: the `NodeEmitter`/`EmitContext`/`NodeEmit` contract (`src/games/space-engineers/codegen/types.ts`) is genuinely language-neutral, but every concrete emitter and the whole program-shell emission in `generate.ts` (constructor/`Main`/dispatch switch) is raw, non-abstracted C# text. **Conclusion: each game owns its own parallel `codegen/` module, not a shared backend** — there is no useful shared intermediate representation to extract, only a shared *taxonomy* to informally reuse. What does carry over as-is across every game: `src/types/graph.ts` (`NodeDefinition`/`ScriptNode`/`NodeConnection`/`GraphSaveData`), `src/lib/graphAssembly.ts` (ref-addressed DAG assembly + layered layout, takes `definitionsById` as a parameter — already game-agnostic), the graph store/undo-redo/autosave machinery, and all canvas/property-panel/palette/validation UI chrome.

Routing: `HashRouter` (`/` → `LandingPage`, `/:gameId` → `Editor`) — chosen over `BrowserRouter` because GitHub Pages has no server-side rewrite to fall back unmatched paths to `index.html`; a hash URL needs no such fallback. Unknown `:gameId` redirects to `/`.

Per-game isolation: `GraphStoreProvider` (`src/store/GraphStoreProvider.tsx`, context/hooks split into `src/store/graphStoreContext.ts` to keep React Fast Refresh happy — a file mixing component and non-component exports disables it) creates a fresh `createGraphStore()` instance keyed by the active `Game` (via a React `key` on the provider, so React fully unmounts/remounts on game switch) — own undo history, own autosave key (`wirerig:<gameId>:graph`), so switching games can never leak state between them.

### Stationeers IC10 (Milestone 9)

Built first, per the plan: no block-API surface to design against, and the hardware's own 128-line/90-char-per-line cap keeps any one graph small even with a full-sized catalog behind it. See `docs/ic10-api-notes.md` for the full sourcing breakdown and instruction-coverage reconciliation; the load-bearing facts that shaped the design:

- 128 lines max, 90 chars/line max (`Game.lineLimit`, checked by `generateScript` and shown in `ScriptPreview` — see "Multi-game architecture" below for the `charLimit`/`lineLimit` split that made this display generic instead of Space-Engineers-only).
- 16 general-purpose registers (`r0`-`r15`) plus reserved `sp`/`ra`; device pins `d0`-`d5` (+`db` for the IC's own housing) — a closed 7-value combo, not player-named free text like Space Engineers' `BlockName`.
- **Labels are natively supported** — `j`/branch instructions accept a label name directly; the in-game assembler resolves it to a line number itself. This turned out simpler than the original plan assumed: codegen never computes absolute line numbers, it just emits `L<Number>:` per node and `j L<target>` — the same "one label per node, referenced by id" shape as Space Engineers' `Step_N_Title()` methods, just a jump instead of a call.
- The chip's instruction pointer persists across game ticks rather than restarting from line 0 (unlike Space Engineers' `Main()`, re-invoked every tick) — so every node's compiled block always ends in an explicit jump (defaulting to a jump back to Start when a port is unconnected), since nothing here resembles a call stack to fall back to.
- Device I/O (`l`/`s` against a `LogicType`) is the same "read/write a block property" shape as Space Engineers' terminal-property emitters, just register-based instead of interface-based. `LogicType` stays a free-text field (not a closed combo — availability is genuinely per-device), but does get a suggestion picker once a `DeviceType` is chosen — see "Device/LogicType data" below.

**Catalog** (35 nodes, `src/games/ic10/nodeLibrary.ts` — a hand-authored TypeScript array, not a JSON asset, since unlike Space Engineers' data this content is original, not reused third-party data), by category:

- **Control** (6): `Start`, `Sleep`, `Yield`, `Loop To Start`, `Call Subroutine`/`Return From Subroutine` (a `jal`/`j ra` pair — reusable node sequences from multiple call sites, useful for staying under the line cap).
- **Devices** (9): `Read`/`Write Device Property` (by pin), `Read`/`Write Device Property (By ID)` (`ld`/`sd`), `If Device Connected`/`Device Connected?` (branch vs. value form of `bdse`/`sdse`), `Check Device Supports LogicType` (`bdnvl`/`bdnvs`), `Read Device Reagent`/`Get Reagent Item Hash` (`lr`/`rmap`).
- **Batch Devices** (4): `Batch Read`/`Write Device Property` (`lb`/`sb`, or `lbn`/`sbn` when a device name is given) and the slot equivalents (`lbs`/`lbns`/`sbs`) — network-wide, addressed by device-type hash rather than a pin.
- **Slots** (2): `Read`/`Write Slot Property` (`ls`/`ss`) — a single device's inventory slots.
- **Variables** (3): `Set Number`, `Number Math` (one `Operator` combo covering 50 instructions — arithmetic, trig, bitwise, shifts/rotates, the `s`-prefixed set-compare family, `Clamp`/`Lerp`/bit-field extract-insert, `Random`), `Select` (ternary).
- **Checks** (1): `Compare` (branches True/False; one `Operator` combo covering 33 instructions via two automatic optimizations — see below).
- **Stack** (9): `Push`/`Pop`/`Peek`/`Poke`, `Get`/`Put Stack Value` (+ By-ID variants), `Clear Device Stack` (+ By-ID variant).

No Templates/Wizards for v1 (all optional on `Game`). See `docs/ic10-api-notes.md` for the full 154-instruction reconciliation (119 directly covered, 3 reachable-but-not-literally-emitted, 8 reachable-but-unoptimized, 24 deliberately excluded — relative branches/`jr` redundant with label-based jumps, `alias`/`define`/`label` redundant with this app's own variable/literal model, `hcf` destructive).

**Device/LogicType data** (added after the initial 9-node catalog shipped, then extended again for the batch nodes): `LogicType` was originally free text with just a Stationpedia hint, since Stationeers has ~486 device types with no official public per-device data file (unlike `NodeLibrary.json`) — a full per-device mapping would normally require running a Stationpedia-extraction mod against the actual game. Worked around by compiling 145 devices/1546 logic-parameter rows (plus each device's prefab hash, where the wiki documented one — 99 of 145 do) from the Stationeers Community Wiki's per-device pages by hand (that site is Cloudflare-Turnstile-gated, blocking both this tool's fetch capability and an automated browser — gathered via a real browser session instead, handed in as a markdown export, parsed into `src/games/ic10/deviceLogicTypes.json`; see `docs/ic10-api-notes.md` for the full sourcing/licensing note). Added a `DeviceType` combo property to the device-pin nodes — **UI-only** there, since a graph's `Device` property is just a physical IC pin (`d0`-`d5`/`db`), not a guarantee of what's actually wired to it in-game; it only scopes the `LogicType` suggestion picker (`src/components/PropertyPanel.tsx`'s `logicTypeFieldAccess`, reusing the existing `ItemPicker` component from Space Engineers' `ItemId` picker rather than building a new one). The **batch** device nodes are the one place `DeviceType` is more than a hint: their compiled `lb`/`sb`/... instructions address a device by network-wide type hash, so `DeviceType` there resolves through `prefabHashFor()` to a real operand (warns if the chosen type has no known hash), and the dropdown is filtered to `deviceNamesWithHash` only. `Game.logicTypeCatalog` is the `Game` field carrying the LogicType-suggestion side of this — a device-scoped alternative to the flat `itemList`/`ItemPicker` pattern, for the case where valid suggestions depend on a sibling property's value rather than being one fixed list. Device names/reagent names that need to reach the compiled instruction (batch device-name filter, reagent lookups) go through IC10's own `HASH("name")` compile-time expression rather than a numeric hash we'd have to source ourselves.

Codegen (`src/games/ic10/codegen/generate.ts`) is flat and label-based — no recursive method calls, no classes, no tick-budget/recursive-mode split like Space Engineers has, since there's no call stack to protect:

- Reuses `findStartNodes`/`getReachableNodeIds` from `src/lib/graph.ts` as-is (already fully generic — a nice confirmation of the Milestone 8 architecture write-up's claim that graph-walk logic doesn't need per-game duplication).
- A small register allocator collects every `Name`-declaring node's variable name (14 `ActionType`s now — Read Device, Set Number, Number Math, Select, Device Connected?, Read Device Reagent, Get Reagent Item Hash, the batch reads, Pop/Peek/Get Stack Value) in first-appearance order among reachable nodes, assigns `r0`-`r15`, and emits one `alias <name> r<N>` line per variable — this is what lets generated code read `l temp d0 Temperature` instead of `l r0 d0 Temperature`. Warns (doesn't error) if a graph declares more than 16 variables.
- Property values (`Value`/`ValueA`/`ValueB`/`ValueC`/...) are either a literal number or a declared variable name, resolved with no bracket syntax needed (unlike Space Engineers' `{name}` interpolation convention) — IC10 accepts a register/alias and an immediate literal in the same operand slot, so whatever the user typed is emitted verbatim; an unresolvable reference becomes a warning rather than a build failure.
- `Number Math`/`Compare` dispatch by operand-count group (nullary/unary/binary/ternary — see `NULLARY_MATH_OPS`/`UNARY_MATH_OPS`/`TERNARY_MATH_OPS` in `generate.ts`) rather than one hardcoded case per operator, so adding another same-shaped instruction later is a one-line opcode-table addition, not a new switch case.
- Both the 128-line and 90-char-per-line caps are checked after generation and surfaced as warnings in the same list `ScriptPreview` already renders (not routed through `ValidationPanel`/`getGraphIssues`, since those only see graph shape, not generated source text — matches how Space Engineers' own size limit is already surfaced via `ScriptPreview`, not `ValidationPanel`, so this isn't a new pattern).

No minifier (source is already terse/line-based; the constraint is line count, not total characters, so a Space-Engineers-style comment-stripping minifier wouldn't help). No `remapLegacyGraph` (no prior desktop tool to import from).

### CC:Tweaked (Milestone 10)

OpenComputers (originally slated as Milestone 11 alongside this one) was dropped: the `MightyPirates/OpenComputers` GitHub repo was archived August 4, 2026 — read-only, maintainers explicitly say no further ports are planned. CC:Tweaked (the actively maintained ComputerCraft fork) is the sole Minecraft-side target.

Unlike IC10 (hard 128-line/90-char cap, no real function-call concept), Lua has real functions, no line cap, and blocking calls (`os.pullEvent` under `os.sleep`, `turtle.forward()`, `rednet.receive()`, ...) that already yield to the game's own coroutine scheduler — so a node-graph-as-flowchart compiles directly to sequential Lua, not an event-handler-registration system. This makes the codegen shape structurally closer to Space Engineers' one-function-per-node approach than to IC10's flat line list. See `docs/cc-tweaked-api-notes.md` for the full sourcing breakdown; the load-bearing facts that shaped the design:

- Every reachable node compiles to one Lua function, `stepN` — same "one label/method per node, referenced by id" shape Space Engineers and IC10 both already use, just a Lua function instead of a C# method or an assembly label.
- **Forward declaration required**: Lua's `local function foo() ... end` sugar can't forward-reference a not-yet-declared sibling, and graphs commonly branch forward — so every step function is declared bare (`local step1, step2, ...`) up front, then assigned a body afterward (`stepN = function() ... end`), the standard pattern for mutually-referencing local Lua functions.
- **Real tail calls, not just recursion**: "go to the next node" always emits as `return stepN()` — a genuine Lua tail call (only valid in that literal `return f(...)` form), not a bare call followed by falling off the function end. Since CC:Tweaked programs commonly loop forever (a turtle mining loop, a redstone monitor loop), this keeps looping in O(1) stack space indefinitely instead of growing the call stack every iteration and eventually hitting Lua's stack limit.
- **No register cap, no minifier, no size limit**: unlike IC10's 16 hard-capped registers, Lua locals are unlimited — every node that declares a named variable just gets one `local` up front (a shared upvalue every step function can read/write), no allocator needed beyond checking the name is a legal, non-reserved Lua identifier. Nothing about CC:Tweaked forces a line/char cap the way IC10's editor does, so `Game.lineLimit`/`charLimit`/`minify` all stay unset for this game.
- No `remapLegacyGraph` (no prior desktop tool to import from) and no wizards/itemList for v1, same "optional field, add later if useful" posture IC10 shipped with.

**Catalog** (47 nodes, `src/games/cc-tweaked/nodeLibrary.ts`, hand-authored TS array — original content, no third-party JSON to reuse, same posture as IC10), by category: Control (Start/Wait Seconds/Loop To Start/Print/Custom Code), Checks (Compare Numbers/Text Equals), Variables (Set Variable/Number Math/Join Text), Peripherals-generic (Peripheral Present?/Call Peripheral Method — the universal escape hatch every dedicated peripheral node is really just a pre-filled version of), Redstone (digital+analog read/write), Rednet (Open Modem/Host Protocol/Send/Broadcast/Receive), Turtle Movement (forward/back/up/down/turn left/right), Turtle World (Dig/Place/Detect/Inspect, each with a Forward/Up/Down Direction combo instead of three duplicate nodes), Turtle Inventory (Select Slot/Get Item Count/Get Item Detail/Suck/Drop/Refuel), Turtle Navigation (Get GPS Position/Get Fuel Level), Monitor (Clear/Write/Set Text Scale/Set Colors), Speaker (Play Note/Play Sound), Disk Drive (Is Present?/Eject).

This catalog is scoped deliberately larger than IC10's 35 nodes despite following the same "hand-authored, non-JSON" pattern: IC10's small catalog is small *because* its hard line cap makes a large graph physically impossible regardless of catalog size, a constraint CC:Tweaked doesn't share. Since this tool targets non-engineers, a "Custom Code" escape hatch exists for genuine gaps but isn't a substitute for dedicated coverage — the right comparison for scope is Space Engineers' catalog (large, but streamlined: one node per distinct capability, a Direction/Side combo instead of duplicate per-direction node pairs), not IC10's cap-driven minimalism.

**Advanced Peripherals addon** (22 nodes, `src/games/cc-tweaked/advancedPeripherals.ts`) — a popular, actively maintained CC:Tweaked addon mod (docs.intelligence-modding.de). Introduced the new optional `Game.addons?: GameAddon[]` field (`src/types/game.ts`): a `GameAddon` is `{ id, label, description, nodeDefinitions }`, gated behind a palette checkbox toggle rather than always shown, since its peripherals only exist if the player has the mod installed. Codegen needs **no** addon-awareness at all: an addon node's `ActionType` (`MeGetItemCount`, `RedstoneIntegratorRead`, ...) is registered in the exact same emitter switch as every base `ActionType` in `generate.ts`, so a graph that already places an addon node keeps generating correctly even after the toggle is switched back off — the toggle is a palette-availability concern only, same as how disabling a Space Engineers DLC block category wouldn't retroactively break a saved graph referencing one. Covers ME Bridge/RS Bridge (list/get-count/push/pull/craft item — both storage mods expose the same method shape), Chat Box (server + private messages), Redstone Integrator (any-side digital I/O), Colony Integrator (MineColonies stats), Environment Detector (time/moon phase/light level), Player Detector (in-range/nearest), and Energy Detector (stored/flow) — every node still compiles through the base catalog's own generic `peripheral.call(side, "method", ...)` shape, just pre-filled.

**Templates** (3, `src/games/cc-tweaked/scenarioTemplates.ts`, same `buildScenarioGraph`/ref-addressed-DAG pattern as IC10's): Tree Farm (poll-detect-chop-replant loop), Tunnel Miner (fuel-check-then-dig-and-move loop, with a graceful "keep rechecking every 10s instead of stopping" out-of-fuel branch rather than a hard stop), and Chest Space Monitor (counts occupied vs. total chest slots onto a monitor every 5 seconds) — the last one is deliberately built around the "Custom Code" node rather than the dedicated catalog, since counting occupied inventory slots needs a small loop over `peripheral.call(side, "list")` that no single dedicated node covers, making it a natural first example of the escape hatch. All three assemble with zero validation errors and zero codegen warnings (`scenarioTemplates.test.ts`, mirrors IC10's template test).

## New feature: Minify

No prior art to reuse — new functionality. Since we own the generator output format exactly, a full parser isn't needed: strip `//` line comments and blank-line runs, trim per-line leading indentation, leave string literals untouched (our own generator never emits `//` inside a string, so a line-based strip is safe). Toggle next to the script preview; live char count against the game's real programmable-block limit (100,000 chars, confirmed against the in-game editor) for both minified and unminified sizes — green under 80,000, amber 80,000–95,000, red above 95,000, with the count itself always shown so it's not just a color guess.

### Native catalog cleanup (context for 7.2/7.3)

`NodeLibrary.json` is ChaosVROne's own published data, reused verbatim (credited in `src/data/README.md`); the fragmentation below is inherited from it, not introduced by this project. Decisions on **how** to fix it are being made now so the design doc in 7.2 doesn't drift from what actually shipped in Milestone 2's data layer:

- **Cross-category duplication** ✅ done — `SetBlockEnabled`, `SetSensorEnabled`, `SetHingeEnabled`, `SetRotorEnabled`, `SetMergeBlockEnabled`, and 9 other `*Enabled`/boolean-toggle `ActionType`s already compiled to identical code across their on/off preset pairs; each pair is now one node with an `Enabled`/`Locked` combo (kept per-context, e.g. `Light Enabled` vs `Thruster Enabled`, for palette discoverability — not collapsed across contexts). AI-Block and Event-Controller presets (which already had a generic combo node alongside their on/off pairs) had the presets deleted outright rather than re-merged. The same duplication also turned up in the Wheel category outside the `*Enabled` naming pattern — `Wheel Propulsion/Steering/Brake/Invert Steering/Invert Propulsion On`+`Off` are `SetTerminalBool` presets differing only in their `PropertyId`/`Value` defaults, exactly like `SetBlockEnabled`'s pairs — merged those 5 pairs the same way. The other ~23 Wheel presets (`Wheel Set Power`/`Friction`/etc., and the 3-way Override presets) are each a genuinely different terminal property, not duplicates, so those were left alone. See the Status section above for the running catalog count.
- **Missing comparison operators** ✅ done — added a general `Number Compare` node (`ActionType: NumberCompare`) with a full operator combo (`>`, `<`, `>=`, `<=`, `==`, `!=`); `If Number Greater/Less Than` are untouched (existing graphs keep working) rather than replaced.
- **Above/Below pairs** ✅ done — Battery, Gas Tank, Cargo, Room Oxygen, Ship Speed, Jump Drive Charge, and Piston Position each shipped as two nodes differing only in comparison direction, fragmented across three different codegen dispatch mechanisms (plain `ActionType` emitters, `ExtendedBuiltin` id-keyed emitters, one-off `ActionType`s like `CargoPercentBelow`/`BatteryBelow`). Unified onto 7 new dedicated `ActionType`s (`BatteryThreshold`, `GasTankThreshold`, `RoomOxygenThreshold`, `CargoThreshold`, `ShipSpeedThreshold`, `JumpDriveChargeThreshold`, `PistonPositionThreshold`), each using the new `blockThresholdCondition` factory (`factories.ts`/`emitters.ts`) that reads a `Direction: Above|Below` combo property instead of baking the operator into a separate node.
- **Preset-only duplicates** ✅ done — `Button Command: dock/mine/startup` deleted; their `Argument` values are preserved by the legacy importer as property overrides onto the plain `Button Command` node.
- **Fused vs. composable duplication**: some measurements (e.g. battery charge) ship both as a fused check (now `Battery Threshold`, after the Above/Below merge above) *and* as a composable primitive (`Get Battery Charge %` + a comparison) that does the same thing. Keep the fused, single-node form as the canonical path for simple threshold checks — one node beats two wired together for the common case — and keep `Get X %` around only for cases that need the raw value for something else (LCD display, custom math). Importing a legacy fused-check node is then a 1:1 relabel onto the merged node, not a graph rewrite; a rewrite is only needed for legacy nodes that have no fused equivalent at all in the cleaned catalog. Not revisited further this pass — already true of the current catalog, nothing left to merge here.

### Property-as-input

Raised while working 7.2: a `NodeDefinition` property (e.g. `SetBlockEnabled`'s `Enabled`) used to be a literal baked in at graph-design time only — no way to wire it from something computed elsewhere in the graph (a variable, a check's result, the PB argument). Two ways to get there, different cost:

- **Interpolated property values** ✅ shipped — properties stay plain strings, but `resolvableBool`/`resolvableNumber` (`factories.ts`) recognize a whole-value `{name}`/`{bool:name}`/`{num:name}` reference (reusing the interpolation syntax Echo/LCD-text already had for mid-string references) and emit `GetBool(...)`/`GetNum(...)` instead of a literal. No new port/edge concept, no store changes — just this check ahead of literal-izing a value, plus a `{ }`/`Fixed` toggle button in `PropertyPanel` next to combo/bool fields (which are otherwise a fixed `<select>` with no room to type a reference). Small, shipped fast, but it's a convention layered on strings rather than a first-class graph connection — React Flow doesn't draw a wire for the dependency, and a node can only take **one** such reference per property (whatever fits in that one string field).
- **Data ports** — not started; the follow-up if interpolation turns out to be limiting. Add a second port kind beyond today's pure control-flow `Handle`s (`Next`/`True`/`False`/`In`), so e.g. `SetBlockEnabled` gets a `Value` input handle wireable from a `Get Bool Variable` node's output — and unlike a single interpolated string, a node can expose **as many data-input handles as it has properties**, each wired independently (a node needing three inputs, e.g. a fused `Number Compare`-style node fed by three different variables, isn't expressible with interpolation alone). Correct long-term shape (matches how most node-graph tools do this) but a large change: React Flow node component needs a second handle type, `NodeConnection`/the store need to distinguish control vs. data edges, codegen needs to resolve a data edge to an expression instead of a statement, and validation needs new rules (data ports must resolve to exactly one source, no cycles). Not mutually exclusive with interpolation — the `{name}` syntax could stay as what an eventual data port's codegen resolves to internally, or as the escape hatch for nodes that don't warrant a dedicated port.

### If-node consolidation: audit + merge (True/False, Above/Below pairs)

Prompted by a direct question about whether the 76-ish "✅ Checks"-category nodes (plus scattered `If...Above/Below`/`...True/False` pairs in other categories) still had unmerged duplicate-pair debt after the earlier Above/Below passes. A full sweep (every node whose Title ends in `Above`/`Below`/`True`/`False`, checked for a same-shape sibling with the opposite suffix) turned up 8 more pairs, all merged the same way as the earlier Above/Below work — a `Direction: Above|Below` or `Value: True|False` combo replacing two nodes:

- **Terminal-property checks** (AI Block, Event Controller, and the generic "Any" nodes each had their own True/False + Above/Below pairs, since all three reuse the same `GetValue<T>` terminal-property shape): `If AI/Event Controller/Any Bool Property` (was `*BoolTrue`/`*BoolFalse`) and `If AI/Event Controller/Any Float Property` (was `*FloatAbove`/`*FloatBelow`) — 6 pairs → 6 nodes, via two new shared factories (`terminalBoolPropertyCondition`/`terminalFloatThresholdCondition` in `factories.ts`, mirrored in `emitters.ts`'s local copy for the AI/Event Controller entries, matching the existing duplication convention between those two files).
- **Rotor RPM/Angle, Hinge Angle** thresholds — `Rotor RPM Threshold`, `Rotor Angle Threshold`, `Hinge Angle Threshold` replace their Above/Below pairs via the existing `blockThresholdCondition` factory (same one the original 7 Above/Below merges used).
- **If Bool Variable** — `ext.bool.if_true`/`ext.bool.if_false` (checks a *variable*, not a terminal property — different emitter shape from the above) merged into one node with a `Value: True|False` combo.

285 catalog nodes (was 295). The sweep found no more True/False or Above/Below duplicate pairs. (Deliberately *not* touched: state-named pairs like `If Piston Fully Extended`/`Retracted` or `If Air Vent Pressurized`/`Depressurized` — those aren't simple direction/boolean flips of the same measurement the way Above/Below pairs are, so a generalized merge there would be a `Door State`-style named-state combo, a different and separate design question from what was asked here.)

A follow-up question ("isn't `If [block type] Enabled/Working` the same as `If Block Enabled/Working`?") caught a related but different duplication the Above/Below sweep didn't check for: **identical emitters under different names**, not same-shape opposite-direction pairs. `IfAiBlockEnabled`/`IfEventControllerEnabled` and `ext.timer.if_enabled` all called the exact same `blockCondition('IMyFunctionalBlock', v => `${v}.Enabled`)` as `If Block Enabled` — same for `*Working` and `isWorkingCondition()`. Confirmed by grepping every `blockCondition`/`isWorkingCondition` call site for duplicate arguments rather than by title pattern. Deleted `If AI/Event Controller Block Enabled/Working` and `If Timer Enabled` outright (same treatment as the earlier `Set AI Block Enabled`-style preset folds — a generic equivalent already existed, so no merged node needed, just delete + enrich the generic one's `Search` + legacy remap). Also let `isWorkingCondition` itself be deleted from `emitters.ts` as dead code once nothing called it anymore. 280 catalog nodes now. Worth flagging as a **different kind of check** to keep running periodically as the catalog evolves — the Above/Below sweep (same title, opposite suffix) wouldn't have caught this, since `If AI Block Enabled` and `If Block Enabled` don't share a title pattern at all, only an identical emitter call.

### Property library for Get/Set-Property nodes (documented, not started)

Raised as real friction: `Set Any Bool/Float/Int/Text Property` and the AI Block/Event Controller property nodes all take a free-text `PropertyId` with zero autocomplete or validation — a user has to already know the exact terminal property id (`"HasTarget"`, `"IsTriggered"`, ...) for the specific block type they're targeting, with no in-app reference. Asked whether the property's *type* could at least be inferred from a library — answer: only if that library exists as structured data, which it currently doesn't anywhere in this repo.

The path: `docs/space-engineers-codegen-api-notes.md` already cites two public API reference sources used while building the `ExtendedBuiltin` emitters — https://malforge.github.io/spaceengineers/pbapi/ (third-party, reportedly more complete than the official docs for some blocks) and https://keensoftwarehouse.github.io/SpaceEngineersModAPI/ (official). A future `src/data/terminalProperties.json` sourced from those two (interface → `{ PropertyId: "bool"|"float"|"long"|"string" }`, in the same spirit as `nodeLibrary.json` — factual signature data, not copied prose) is what an autocomplete/type-check would key off. Once that data exists:
- **PropertyPanel** could offer a `<datalist>`/autocomplete on `PropertyId` scoped to the node's target interface (would need each `Set/Get Any * Property` node to declare which interface it targets, e.g. via a new `NodeDefinition` field or a small id→interface lookup next to the JSON).
  - **Type inference** (the second half of the question) becomes possible once the library exists: look up `PropertyId` in the per-interface map and either warn if the node's own type (`SetTerminalBool` vs `SetTerminalFloat`) doesn't match, or — further out — collapse the four typed `Set Any * Property` nodes into one that infers `T` from the chosen `PropertyId` instead of needing four separate typed nodes.

Not started — this is a real, scoped data-curation project (going through two API references block-by-block) before any UI work makes sense.

### Dynamic-output-count Switch node (Milestone 12, done)

Asked how hard a Switch/Match node would be — one where the user picks the number of output cases in the UI (not the compiled code; codegen already handles however many ports a node instance ends up with). More tractable than it sounds, because two of the three needed pieces already exist:

- `ScriptGraphNode` (`src/components/ScriptGraphNode.tsx`) already renders `scriptNode.OutputPorts` — the **per-instance** array — not `definition.OutputPorts`, so the canvas already supports a node whose port count differs from its catalog definition's.
- `Command Router`/`Number Greater Router` already prove the codegen pattern: loop over however many output ports exist, one `Property` per port (`StartupArgument`, `Threshold2`, ...), emit one case/comparison per port. A dynamic Switch's emitter is the same loop, just not hardcoded to a fixed port list.

What's actually missing: **nothing today lets a user add/remove ports on an existing node instance** — `ScriptNode.OutputPorts` is copied once from `NodeDefinition.OutputPorts` at add-time and never mutated afterward. That needs:
1. A store action (`addOutputPort`/`removeOutputPort`, or a single `setOutputPorts`) mutating both `OutputPorts` and the corresponding per-case `Properties` entries on one `ScriptNode`.
2. A "manage cases" control in `PropertyPanel` for this node specifically — +/− buttons, each case getting a match-value field — plus a match-mode choice (equals/dictionary dispatch vs. an if/else-if chain, which differ slightly in emitted code: a `switch` needs distinct constant case values, an if/else-if chain doesn't).
3. A new emitter that reads however many `Case<N>Value` properties exist (mirroring `Command Router`'s pattern) and emits the chosen dispatch shape.

Estimate: comparable in size to the Number Math/Number Compare work from Milestone 7.2 — one clearly-scoped new feature, not a foundational change, since the rendering and codegen precedents already exist. Space Engineers-only for now (the store action/PropertyPanel control are generic UI, but `Command Router`'s dispatch-by-argument-string emitter is SE-specific; a MIPS/IC10 or Lua equivalent would need its own emitter once those backends exist).

Shipped as `logic.switch` (Title "Switch"): one `Value` property (a fixed string or a `{var}` reference — see below) and any number of `CaseN`/`CaseNValue` output ports plus a `Default` fallthrough. `switchEmitter` (`src/games/space-engineers/codegen/logicEmitters.ts`) loops `node.OutputPorts` (the per-instance array, not the catalog definition's) and emits one `case` per port found — same shape as `commandRouterEmitter`, just not hardcoded to a fixed port list. No new architecture was needed: `ScriptGraphNode` already rendered per-instance ports, and `getGraphIssues`/reachability were already port-list-generic.

**Generalized to Command Router and Number Greater Router too** (not just Switch), since both are shaped the same way (one input, N user-manageable cases, one fixed terminal/fallback port). The store side is fully generic: `addOutputCase`/`removeOutputCase` (`src/store/graphStore.ts`) take an `OutputCaseConfig` — `terminalPort`, `nextPort`, `isRemovable`, `propertyKey`, `defaultValue` — supplied by the caller, so the store itself carries no per-ActionType naming knowledge (mirrors how `Game`-specific behavior is threaded in elsewhere rather than baked into shared infra). `PropertyPanel` builds one `OutputCaseConfig` per ActionType (`OUTPUT_CASE_CONFIGS`) and renders the same "+ Add Case"/"− Remove Case" pair for all three:
- **Switch** — every case is user-managed from the start (`isRemovable: () => true`), matching the original design.
- **Command Router** — went further than "generalize while keeping the 11 built-ins": those fixed named ports (`startup`, `dock`, `mine`, ...) added real per-case rendering/routing complexity for cases most graphs never used. Dropped entirely in favor of the exact same `CaseN`/`CaseNValue` scheme as Switch (`caseNConfig('unknown')` in PropertyPanel, shared with Switch's `caseNConfig('Default')`), pre-wired to `_argument` instead of a `Value` property — so Command Router is now just "Switch that already knows what to switch on." Ships with 3 default cases (`Case1`/`Case2`/`Case3` = `startup`/`shutdown`/`status`) rather than Switch's 2, chosen so the existing "Remote Command Panel" scenario template didn't need restructuring, just its edges re-pointed from the old semantic port names to `Case1`/`Case2`/`Case3`. `commandRouterEmitter` now loops `node.OutputPorts` (skipping `unknown`) exactly like `switchEmitter` loops `Default`.
- **Number Greater Router** — its original `Greater2`..`Greater6`/`Threshold2`..`Threshold6` already used a plain-numeric scheme, so growing past 6 needed no new naming convention at all — `Greater7`/`Threshold7` and beyond just work. Those original 5 stay non-removable (unlike Command Router, dropping them wasn't needed — the numeric scheme was already generic); `numberGreaterRouterEmitter` now derives its threshold property key from the port name (`numberGreaterRouterThresholdKey`) and sorts whatever `GreaterN` ports exist descending, instead of iterating a fixed 6→2 array.

**Bug found and fixed while building this: `break;` could land inside a `//` comment.** Every `case`/`default`/branch line that embeds `ctx.next(node, port)` inline (`case "x": ${ctx.next(...)} break;`) assumed `ctx.next()` always returns a real statement — but for an unwired port it returns a bare `// "Port" not connected` comment instead, with no trailing semicolon-terminated statement. Concatenating `break;` (or a closing `}`) *after* that comment puts it inside the comment, where `minifySource`'s `//`-to-end-of-line stripping deletes it right along with the comment — silently turning an unwired switch case into a fallthrough, or unbalancing braces, in the *minified* output only (the unminified version looks fine, since the comment still visually ends the line there, which is exactly why this stayed unnoticed). Fixed with two small ordering helpers that check `ctx.hasNext()` first and put the real syntax (`break;`, the closing `}`) *before* the comment instead of after when the port is unwired: `caseLine` (`logicEmitters.ts`, used by `switchEmitter`/`commandRouterEmitter`) and `nextBlock` (`factories.ts`, used everywhere an inline `if (...) { ${ctx.next(...)} }`-shaped branch exists — `numberGreaterRouterEmitter`, `repeatTimesEmitter`, and three `extendedEmitters.ts` multi-way status routers). `testUtils.ts`'s `fakeContext()` now takes an optional `unwiredPorts` set so emitter unit tests can actually exercise the unwired path instead of only ever hitting the (bug-free) wired one.

Also added the "insert variable" picker to Switch's `Value` field (the one thing genuinely new to Switch specifically): a `resolvableText` factory (mirrors `resolvableBool`/`resolvableNumber`) resolves `Value` to a fixed string literal or, for a pure `{name}` reference, `GetText`/the variable's own backing field — restricted to text-kind variables in the picker (`kinds={['text']}`) since a Switch's case literals are always strings.
